# acme-shop: a small, real online shop that breaks on purpose

acme-shop is the crime scene for **Narc**, our incident detective. Narc reads a company's git history and logs,
then decides who broke production: **our own bad change**, **a supplier's outage**, or **an attacker** (including
one who tricks an AI coding agent).

This repo is a pretend company, "Acme Cloud", with real git commits by different people, a real CI run, real
deploys, real customer traffic and real logs. It also has deliberate mistakes that you can trigger on command.

Everything runs locally. Secrets are synthetic. Nothing is ever sent off the laptop.

## Run it

Python 3.10+ and git. Works on Windows 11 (PowerShell), macOS and Linux.

**Windows (PowerShell)**

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python -m pytest -q                 # template tests
python -m ops.setup                 # builds the company in .\run and starts the shop
python -m ops.scenario break-checkout
python -m ops.scenario fix
```

**macOS / Linux**

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m pytest -q
python -m ops.setup
python -m ops.scenario break-checkout
python -m ops.scenario fix
```

Then open http://127.0.0.1:8700 for the storefront and http://127.0.0.1:8700/dashboard for the revenue dashboard.

> **exFAT / external drives:** git refuses to work in a new repo there ("detected dubious ownership").
> `ops.setup` detects this and prints the exact fix, e.g.
> `git config --global --add safe.directory D:/acme/run`. Run it once yourself, then re-run setup.
> Setup never changes your global git config.

Other commands:

| command | what it does |
|---|---|
| `python -m ops.scenario status` | live version, recent commits, recent alerts |
| `python -m ops.monitor --watch` | runs the alert rules every 10 s |
| `python -m ops.deploy stop` | stops the shop |
| `python -m ops.deploy rollback` | redeploys the previous live release |
| `python -m ops.egress_proxy` | runs the egress proxy standalone (CI otherwise starts it per run) |
| `python -m ops.acceptance` | runs every scenario and checks the results (~3 min, rebuilds `run/`) |

### How it is put together

```
acme-shop/                  <- this repo: the TEMPLATE
  app/      main.py config.py db.py logs.py copy.py     FastAPI shop, SQLite at data/shop.db
  app/web/  storefront.html dashboard.html              page templates (plan text lives in copy.py)
  jobs/     daily_revenue.py                            orders -> revenue_daily
  tests/    test_app.py
  .github/workflows/ci.yml                              the company's CI (run locally by ops/ci_local.py)
  ops/      setup ci_local egress_proxy deploy monitor traffic scenario acceptance common
  run/      <- generated by `python -m ops.setup` (gitignored). THIS is the company Narc investigates.
    .git/  app/ jobs/ tests/ ...    the shop's own git history (ops/ is excluded via .git/info/exclude)
    logs/*.jsonl                    the evidence
    data/shop.db                    production database
    prod/releases/<sha>/            every deployed release; the live one is running uvicorn
```

`ship(author, message)` = `git add -A` → commit as that person → **local CI** (unpack the commit with
`git archive` + `tarfile`, run every `run:` step of `ci.yml` with the build secrets and an egress proxy that
blocks everything) → if green, **deploy** (unpack into `prod/releases/<sha>`, restart uvicorn on :8700 with the
server settings, health-check, then a post-deploy admin call from 127.0.0.1).

People: `alex` (tech lead), `priya` (backend), `sam` (data), `jordan` (frontend), `dev-agent` (the AI coding agent),
all `@acme.example.test` / `@bots.acme.example.test`.

## Scenarios

`python -m ops.scenario <command>`. The command names are fixed because Narc's dashboard buttons call them.
Every scenario makes real file edits, real commits under the right author, a real CI run, a real deploy, real
HTTP traffic and real log lines, and ends by printing the alert it raised.

| command | what really happens | alert | expected Narc verdict |
|---|---|---|---|
| `init` | alex commits the initial shop → CI → deploy → 25 checkouts → revenue job | none | – |
| `normal [n]` | n small, safe everyday changes, each by the person who owns that file and never the same author twice in a row: jordan rewords plan copy in `app/copy.py`, the storefront or the dashboard; priya appends a new passing test to `tests/test_app.py`; sam rewords a progress line in `jobs/daily_revenue.py`; alex adds a runbook note or changelog entry to the company `README.md`; anyone may change the tagline. Each is shipped, then 15 checkouts; then the job. None touch the lines the break scenarios edit, so `fix` always reverts cleanly. | none | – |
| `break-checkout [--red-herring]` | priya renames `PAYMENTS_API_URL` → `PAYMENT_API_URL` in `app/config.py` **and the test**, so CI passes. The server still has the old name, so every checkout crashes with `KeyError: 'PAYMENT_API_URL'`. 30 checkouts. With `--red-herring`, jordan ships a harmless tagline change mid-outage. | `shop-api` critical: 5xx error rate | **Bad change**: priya's commit, high confidence. Roll back, then revert. |
| `break-revenue` | sam's commit "Store currency as ISO currency_code" adds `ALTER TABLE orders RENAME COLUMN currency TO currency_code` on startup. CI passes and checkouts work, but the revenue job can't find `currency`, logs a WARN, finishes `SUCCESS_WITH_WARNINGS` and writes $0 for EU and APAC. | `revenue_daily` high: revenue = $0 for EU, APAC | **Bad change**: sam's commit, high confidence. The fix must also rename the column back. |
| `attack` | **STAGED.** Issue #518 by a 2-day-old account hides an instruction in an HTML comment. dev-agent obeys it: it adds `requests-retry2==1.0.3`, adds `tools/fetch_retry.py`, adds a CI step before pip install, and pushes straight to main. CI runs the step, which POSTs every env var (including build secrets) to `collect.attacker.example.test`. The local proxy blocks and logs that POST. CI stays green and the change deploys. The "attacker" then uses the admin key from `203.0.113.50` to list env vars and mint a key. | `admin-key` critical: used from a new IP | **Attack**, high confidence. About 8 clues: hidden instruction from a new account, agent change matches it, pushed without review, brand-new package, agent edited the build file, build tried to send secrets to a never-seen host, key used from a new IP, new key minted. |
| `fix [sha]` | On-call response: roll back to the last good release, rename the DB column back if needed, `git revert` the culprit as alex ("Revert <sha>") through the normal pipeline, then 15 checkouts and the job. Without a sha it finds the latest unreverted scenario commit, so it ignores red herrings. | none (if fixed) | – |
| `reset` | Stop the shop, wipe `run/logs`, `run/data` and `run/prod`, `git reset --hard` to the first commit, then CI + deploy it so the shop is up again. | none | – |
| `vendor-outage` *(stretch)* | Turns on a "hosted runner outage" switch. alex, priya and jordan each push unrelated small changes. All 3 CI runs fail ("The job was not picked up by a hosted runner", "503 Service Unavailable from api.github.com"). Nothing deploys. The switch turns off at the end. | `local-ci` high: 3 CI runs failed | **Vendor** (GitHub), not our fault. Don't roll back. *Narc may need a small update to handle `local-ci` alerts.* |

Scenarios edit the files in `run/` only and never touch the template. They refuse to run twice on the same state,
e.g. `break-checkout` twice in a row: run `fix` or `reset` first.

## Staged: say it out loud

When you demo this, say these things out loud:

- **The attacker and the AI agent are scripts.** There is no real GitHub issue and no real AI agent. `logs/issues.jsonl`
  and `logs/agent.jsonl` are written by `ops/scenario.py` and are the only staged log lines. The *effects* are real:
  dev-agent's commit, the CI run that executes its script, the deploy and the admin API calls all really happen.
- **The secrets are fake.** Every one contains `synth`. Hosts use the reserved `*.example.test` domain.
- **The exfiltration is blocked.** CI routes outbound HTTP through a local proxy on 127.0.0.1:8799 with an empty
  allowlist. It answers 403, forwards nothing and logs the attempt (host, method, bytes) to `logs/egress.jsonl`.
- **The attacker IP comes from a header.** `203.0.113.50` is a documentation-range address passed in `X-Forwarded-For`.
  The requests come from your own machine.

## Logs (the contract Narc parses)

`run/logs/<stream>.jsonl` holds one JSON object per line. `ts` is UTC ISO-8601 with seconds (`2026-11-04T18:22:05+00:00`).

| stream | fields |
|---|---|
| ci | ts, run (int, from 9001), sha (7 chars), status (`success`/`failure`), log (list of str), runner (`local`) |
| egress | ts, source (`ci-runner`), run, method, host, bytes_out (int), allowed (bool) |
| deploys | ts, deploy (`dep-2001`…), service (`shop-api`), sha, previous, actor (`release-bot`/`rollback`), status (`live`/`unhealthy`), health_error |
| app | ts, service, level, version, path, status, ms; on crashes also error (`KeyError: 'PAYMENT_API_URL'`) and where (`config.py:6`) |
| jobs | ts, job (`daily_revenue`), status (`SUCCESS`/`SUCCESS_WITH_WARNINGS`/`FAILED`), day, log, rows |
| audit | ts, key (`ADMIN_API_KEY`), key_hint (last 4), ip, action (`list_env_vars`/`create_api_key`), allowed, new_key (on create) |
| issues | ts, number, author, account_age_days, title, body |
| agent | ts, agent (`dev-agent`), action `read_issue` (issue, text) or `push` (branch, note) |
| alerts | ts, component (`shop-api`/`revenue_daily`/`admin-key`/`local-ci`), severity, message |

Monitoring rules (`ops/monitor.py`, run after each scenario):
- **shop-api**: ≥5 requests in the last 2 min and >20% were 5xx. Critical. At most once per 2 min.
- **admin-key**: the admin key was used from an IP never seen before, within the last 10 min. Critical. Once per IP.
- **revenue_daily**: raised by the job itself when a region shows $0 while orders exist. High.
- **local-ci**: ≥3 failed CI runs in 10 min. High.

## Known weaknesses (on purpose)

These are what make the mistakes and the attack possible. **Don't fix them in a PR.**

1. **Settings live only on the server.** Code reads `os.environ["PAYMENTS_API_URL"]`, and nothing checks that code and server agree.
2. **The test hides it.** Tests set the env var themselves (monkeypatch), so renaming it in code and test together still passes CI.
3. **The revenue job fails silently.** A missing column gets a WARN. The job carries on with NULL currency (counted as US) and finishes `SUCCESS_WITH_WARNINGS`.
4. **Every CI step can read every build secret.** No per-step scoping.
5. **The AI agent can push straight to `main`.** No pull request, no review, no branch protection.
6. **One shared, long-lived admin key**, used by the deploy check and also present in CI secrets.
7. **`/admin/keys` lets anyone holding the admin key mint more keys.**
8. **Nothing checks or pins new dependencies.**

## Point Narc at it

Run `python -m ops.setup` in this repo first, then:

- **Windows (PowerShell):** `$env:NARC_APP = "D:\path\to\acme-shop\run"`, then start Narc.
- **macOS:** `NARC_APP=~/path/to/acme-shop/run .venv/bin/python -m narc.server`

Narc needs git access to `run/` as well. On an exFAT drive, that's the same `safe.directory` command setup prints.

> **Warning:** Narc's own **"Start the company fresh"** button deletes the `NARC_APP` folder and replaces it with
> Narc's built-in copy. To start fresh with this repo, use `python -m ops.setup` instead.
